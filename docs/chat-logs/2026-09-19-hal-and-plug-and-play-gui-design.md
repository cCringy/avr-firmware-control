# Design chat: HAL pattern & plug-and-play GUI architecture

**Date:** 2026-09-19

---

### Q: how would i write an HAL here

**A:** Walked through the HAL convention already established in `hal/` (`gpio`, `timer`, `adc`, `led`):

1. **Split interface from implementation** — the `.h` exposes only hardware-agnostic types/prototypes, never a register name; the `.c` is the only file that touches `DDRx`/`PORTx`/`PINx`.
2. **Represent hardware selection with enums, not raw numbers** — e.g. `gpio_port_t { B, C, D }`, `Px0`..`Px7`, so callers never hardcode a register or bit index.
3. **Fan out on the enum inside the `.c`, one case per real register** — e.g. `GPIO_set_output` switches on `port` and does `DDRB |= (1 << pin)` / `DDRC |= ...` / `DDRD |= ...`. Repetitive but each branch is a single, datasheet-auditable register op.
4. **Keep functions small and single-purpose**, named `MODULE_verb_noun`. Higher-level modules (`led.c`) compose lower HAL modules (`gpio.c`) rather than touching registers directly — that's the layering.
5. **Board-specific values live one layer up, in `bsp/`** — `hal/timer.h` takes milliseconds not a prescaler, `hal/adc.h` takes a channel not a mux value. Choices like baud rate or which pin is the LED belong in `bsp/board_config.c`, not baked into `hal/`.
6. **Return simple status, not exceptions** — `util/status.h`'s `status_t` for anything that can fail.

Template offered for a new module (`hal/foo.h` + `hal/foo.c`) following the same shape.

Flagged one existing inconsistency: `hal/debug_uart.h` has no matching `hal/debug_uart.c` — its implementation lives outside the pattern, in a prebuilt `lib/libdebug_uart.a`, with duplicate/parallel source sitting in `_wip/uart.c` + `_wip/uart_internal.h`. Worth reconciling before building more on top of it.

### Q: How will the user interact with GUI. Does the gui generate main? But how will the user configure the logic

**A:** Established that GUI and firmware are currently **disconnected**:

- **GUI side:** `Main.qml` has Pinout/ADC/Timer/UART tabs. `PinoutInterface.qml` overlays clickable hotspots on the board image (from `pindata/pins.json` via the C++ `PinLoader`), but a click only does `console.log`. `UartInterface.qml` has a `toConfig()` function returning a JS object (baud, mode, framesize, parity, stop bits, U2X, SPI mode) — but nothing calls it or sends it anywhere yet.
- **Firmware side:** `app/main.c` is an empty stub (`while(true){}`). `bsp/board_config.c` is a hand-written `static const config_t cfg = { .uart_baud = 115200, .uart_mode = UART_ASYNC };` that isn't generated by anything, and doesn't currently compile as-is (`config_t`/`UART_ASYNC` aren't defined anywhere reachable from `board_config.h`).

Two fundamentally different architectures were laid out:

1. **Codegen at build time** — GUI settings serialize to a header/struct matching `config_t` (which `toConfig()`'s field names already mirror) → overwrites `bsp/board_config.c` → existing `make`/`avrdude` flow compiles and flashes it. GUI = config editor; MCU has no runtime awareness of the GUI.
2. **Live control at runtime** — GUI talks to the already-flashed MCU over the UART HAL, same protocol as `tools/serial_echo.py`/`serial_plot.py`. Needs a defined serial protocol and firmware that listens for commands in `main.c`.

Given `board_config.c`'s struct shape matches the UART form's fields, codegen looked like the intended direction — flagged for confirmation.

### Q: I want to create a "Plug and Play" user experience. I want the user to be able to configure the mcu without touching any register and focus on the logic

**A:** Asked whether "focus on the logic" meant (a) the user still writes C against a generated HAL config, or (b) a fully no-code visual logic system (blocks/rules/state machine, with all of `main.c` generated).

User: *"well thats what im wondering about. What would be the best solution"*

**Recommendation given:** generated config + named HAL bindings, user still writes plain C for logic — **not** a full no-code visual runtime. Reasoning:

- The ATmega328p has 32KB flash / 2KB RAM — an on-device interpreter is a poor fit, and a full graph-to-C code generator is effectively building a small compiler frontend, disproportionate scope for this project.
- The "plug and play" promise (no register knowledge required) is fully deliverable through configuration alone:
  1. **Pinout tab** — user assigns a role + friendly name to each pin (e.g. "LED1" → Digital Out), building on the existing hotspot UI.
  2. **Peripheral tabs** (UART/Timer/ADC) — configure operating parameters visually, as `UartInterface.toConfig()` already does.
  3. **Generator** emits `bsp/board_config.c` (peripheral params), a generated `bsp/pin_map.h` (named wrappers per pin, e.g. `LED1_on()` → `GPIO_set_pin_high(B, Px1)` — the actual "no registers" layer), and a scaffolded `app/main.c` with all `_init()` calls wired in plus a fenced `/* === USER LOGIC START/END === */` region the generator never overwrites on regeneration.
  4. **Flash button** in the GUI shells out to the existing `make flash`.
- Tradeoff acknowledged: still "writing C," just C with zero hardware knowledge required, not literally code-free. Noted a code-free rule builder could sit on top of this later without rework, as a wizard that emits a line into the fenced region rather than needing a runtime interpreter.

### Q: well if the user writes c my gui is useless no?

**A:** Pushed back on "useless" — the config/peripheral-setup layer (pin muxing, register math, baud-rate/prescaler calculations, conflict detection) is genuinely valuable and error-prone by hand, the same reason tools like STM32CubeMX aren't considered useless despite users still writing their own application logic.

But agreed the underlying concern was valid: a config-only GUI feels thin if the actual point of the project (the logic) happens entirely outside it. Proposed a narrower, declarative layer instead of a full visual language:

- **Rules tab** — pick a trigger (pin edge, timer tick, ADC threshold) and an action (set pin, send UART, start timer) from dropdowns populated by the already-configured pins/peripherals. GUI generates matching `if`/`switch` code directly into the fenced region — genuinely zero-code for the user, no interpreter/VM, just codegen for a fixed set of patterns.
- The **fenced C region remains the escape hatch** for anything beyond what the rule builder can express, so the ceiling isn't capped at trivial projects.

### Q: so youre saying i should use an SPS like logic? Matching Signals to Slots?

**A:** Confirmed — SPS/PLC-style (ladder logic / IEC 61131 I/O mapping) is an accurate description: a fixed vocabulary of **signals** (inputs: pin edge, timer tick, ADC threshold) wired to **slots** (outputs: set pin, send UART, start timer). Noted this pairs naturally with the fact the GUI is already built on Qt's own signal/slot mechanism (`PinoutInterface`'s `pinClicked`/`pinHovered`, `NavBar`'s `Connections { onItemSelected }`), so the UI wiring metaphor and the generated-firmware wiring metaphor line up.

Asked how expressive a single rule should be:

- **One signal → one slot** (e.g. "BTN1 pressed → LED1 toggle") — simplest data model and codegen, one `if` per rule.
- **Multiple signals with AND/OR → one or more slots** — closer to real ladder logic, needs a condition-combining UI and richer codegen.

**User chose: one signal → one slot.**

---

## Finalized design (as of end of this chat)

- **Signals** (generated from configured pins/peripherals): pin edge (rising/falling/change) on a Digital In, ADC threshold crossed, timer tick elapsed.
- **Slots**: set/clear/toggle a Digital Out, send a fixed value/string over UART, start/stop a timer.
- **Rule** = one signal → one slot, built from dropdowns populated only by pins/peripherals the user already configured (so the rule builder can't offer an unconfigured or conflicting pin).
- Each rule compiles to one `if` in the fenced `USER LOGIC` region of `main.c`, calling generated `pin_map.h` wrappers (`LED1_on()`, `BTN1_read()`, etc.). No interpreter, no runtime cost. The user never needs to open the C file unless going beyond what the rule builder covers.

**Open question at end of chat:** whether to scope the full signal/slot vocabulary up front before writing code, or start end-to-end with the smallest useful slice first (pin-role assignment + Digital In → Digital Out rules only, then expand signal/slot types and codegen from there).
